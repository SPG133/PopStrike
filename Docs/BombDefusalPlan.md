# PopStrike 爆破 FPS 开发计划书

版本：2026-09-22。用途：从现有关卡白模与大厅逐步开发到六人可玩的爆破模式。

本文是计划，不表示功能已经实现或测试通过。遵循仓库 [AGENTS.md](../AGENTS.md)，将 [DevelopmentRoadmap.md](DevelopmentRoadmap.md) 的阶段 0–6 细化为当前需求下的实施任务。旧文档的历史检查记录保留；当前进度以代码、编辑器和运行验收共同确认。

## 1. 目标与关键结论

首版目标：现有大厅进入果汁工厂，两队各三人完成准备、交战、安装/拆除炸弹、回合结算、换边和比赛结束；支持一把可靠的步枪、基础动画、最小经济与道具、比分板、小地图、设置，并在独立服务器上验证战争迷雾和弱网体验。

减少反复重构的关键是现在确定数据所有权、生命周期、动作恢复和信息权限。武器数值、动画质量、材质效果可以逐步增加。无法保证永不重构，但可让大多数扩展局限在相关系统内。

本计划采用以下暂定范围，属于项目建议，不是 CS 官方规则，也不是用户已确认的全部玩法：

- 首个规模为 3v3、一张现有地图；先双客户端验收，再扩展六人。
- 积分板先按场景大屏理解：显示实时比分，材质随领先、得分、胜负改变；点击切页作为小扩展。若射击屏幕会影响比赛，需另定义玩法。
- 自定义道具先按开发者制作、玩家选择装备的少量道具理解；不默认实现玩家自由编程或组合技能编辑器。
- 迷雾采用服务器对每个连接限制敌方信息下发；小地图情报显示是相关但独立的规则。
- 回合中死亡进入受限观战，下回合重生；先使用固定装备完成核心闭环，随后接经济与购买。
- 瀑布和水先作为装饰。游泳、水流推力、可破坏水闸等玩法不自动包含在首版。

VALORANT 的官方入门说明将准备购买、攻守交换、爆破目标、枪械、技能与沟通放在同一游戏循环中。对本项目的启发是：道具必须服务于突破、防守、收集信息或争取时间，需要与经济、阶段和信息规则共同设计。[VALORANT 官方入门](https://playvalorant.com/en-us/news/announcements/beginners-guide/)

Epic 的 Lyra 是官方学习样例，可参考装备定义、动画组织、输入和设置；它不是可直接移入当前项目的完整爆破 FPS。当前项目不因导入了一批资产就迁移 Lyra 的整套框架。[Lyra 官方说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/lyra-sample-game-in-unreal-engine)

## 4. 先写清楚一场比赛的流程

```text
主菜单与设置 → 连接 → 大厅组队/准备/地图选择 → 加载比赛
  → 等待参赛者就绪 → 回合准备/购买 → 正式交战
      ├─ 未安装：进攻方全灭或时间耗尽 → 防守方获胜
      ├─ 防守方全灭 → 进攻方获胜
      └─ 合法安装完成 → 炸弹倒计时
          ├─ 拆除完成 → 防守方获胜
          └─ 倒计时结束 → 进攻方获胜
  → 锁定回合结果 → 结算/保枪/清场
  → 未结束：必要时换边 → 下一回合准备
  → 达到比赛结束条件：战绩结算 → 返回大厅或退出
```

上图是首版建议：安装后进攻方全灭不能直接判输；炸弹仍是防守方的任务。防守方全灭可直接判进攻方获胜。双方同归于尽、最后一发与安装完成同刻等边界，必须由服务器统一裁决。

实施回合闭环前完成一页规则表：

| 规则项 | 首版建议/需要确定的内容 | 为什么现在确定 |
|---|---|---|
| 队伍与攻守 | 队伍 A/B 是固定身份；进攻/防守是可切换职责 | 换边时比分、头像与统计不串队 |
| 赛制 | 先核对当前 8 分制、7 回合换边、决胜局随机边；若保留写清楚 | 它并非对称的标准半场方案，不能暗中当作最终规则 |
| 时间 | 准备、交战、安装动作、炸弹、拆除、结算分别配置 | 不共用语义不一致的时长变量 |
| 拆除 | 当前实现有半程检查点；确认是否保留 | CS 式连续拆除与检查点规则会影响状态和 UI |
| 包点 | 先在真实白模核对包点；可先验收一个，最终按布局支持 A/B | 不创建未知坐标，不把包点数量写死到角色 |
| 炸弹 | 唯一实例；指定携带者、死亡掉落、拾取与越界恢复 | 防止多炸弹、无法拾取和掉出地图导致死局 |
| 交互打断 | 死亡、离开范围、切换动作、阶段结束必须取消；受伤是否取消另定 | 服务器持续校验，不能只在按下时检查 |
| 同刻事件 | 按服务器记录时间排序；同时间建议拆除完成优先于爆炸；结果只提交一次 | 不依赖 Timer 回调偶然顺序，规则作为项目选择记录 |
| 死亡与观战 | 首版仅队友视角；全部队友死亡后受限视角 | 避免借观战获取敌方位置 |
| 经济 | 起始资金、上限、胜负收入、连败、击杀/任务奖励、保枪与换边重置 | 保枪和清场不能等购买界面做好才考虑 |
| 友伤/碰撞 | 首版建议关闭友伤；队友阻挡规则单独配置 | 影响投掷物、伤害、出生与地图通行 |
| 断线与加入 | 当前回合新加入先观战；重连保留身份、经济和统计，不立即复活 | 避免通过重连补满血或复制道具 |

热身、加时、战术暂停、投降可在基础比赛稳定后加入。当前等待阶段必须有加载失败/超时处理，不允许无限卡住；正式比赛中一方全部断线要有明确等待与终止策略。

## 5. 让后续扩展集中在相关模块

先保持一个 PopStrike Runtime 模块。下列新增名称都是职责建议，不表示这些类已经存在，也不要求一次创建完。

| 所有者 | 权威状态/职责 | 扩展方式 |
|---|---|---|
| 现有 Connection 与大厅 | 连接、准备、组队、地图选择、切图 | 接入失败和返回大厅流程 |
| 现有 MatchGameMode | 服务器阶段、胜负、出生、回合重置 | 补完现有状态机和合法交互入口 |
| 现有 MatchGameState | 全员允许知道的阶段、比分、公开时间 | HUD 与世界大屏共同订阅 |
| 现有 MatchPlayerState | 稳定身份、队伍、公开战绩；私有数据需过滤 | 跨 Pawn 保留；身份不用昵称匹配 |
| 比赛 Controller | 输入请求、所属玩家 UI、私有情报与观战授权 | 复用拥有者连接，不创建旁路广播 |
| Character + CMC | 身体、移动、第一人称镜头、第三人称网格 | 简单移动先行，特殊移动后续按预测路径扩展 |
| Combat/Equipment | 武器实例、弹药、射速、动作状态 | 同机制武器新增配置；新机制新增局部行为 |
| 单一生命/伤害入口 | 扣血、死亡事件、生命标识 | 子弹、爆炸、道具共用，不各写一套死亡逻辑 |
| 炸弹与包点 | 炸弹物理状态、交互条件、服务器动作计时 | 包点作为地图放置数据，不写进角色分支 |
| 道具执行层 | 激活校验、消耗、冷却、效果生命周期 | 根据具体道具决定小组件或 GAS |
| 信息策略 | 每个接收者可得到实体、标记、声音等何种信息 | 迷雾、小地图、侦察、观战共用规则 |
| UI/AnimBP/音效/材质 | 从当前允许的状态产生表现 | 不产生伤害、资金或比赛结果 |

每种联网状态必须记录：谁写、谁收、存在多久、首次如何初始化、漏消息后如何恢复。

| 数据 | 写入者 | 接收者 | 生命周期与恢复 |
|---|---|---|---|
| 比分/阶段/公开期限 | 服务器 GameMode | 所有参赛客户端 | 一场比赛；通过当前快照恢复 |
| 弹药/私人冷却/资金 | 服务器相关系统 | 拥有者；队友需求另定义 | 装备或比赛；客户端预测后校正 |
| 可见角色位置与姿态 | 服务器 | 当前被授权的连接 | 一条生命；重获相关性重新初始化 |
| 换弹/使用动作 | 服务器 | 拥有者与获授权观察者 | 类型、序号、起始时间、时长和取消状态 |
| 侦察标记 | 服务器信息策略 | 被授权玩家/队伍 | 采样位置、精度、来源、失效时间；过期删除 |
| 枪口火花/单次声音 | 服务器确认或允许的本地预测 | 相关且被授权接收者 | 瞬时；去重、不补播陈旧事件 |
| 按键/灵敏度/画质 | 本地玩家 | 本机 | 本地设置；启动加载、恢复默认 |

状态先初始化再订阅变化，避免控件晚创建时漏掉初始比分。状态通知用于更新显示；倒计时从服务器期限计算，不每秒复制一个倒计时数字。

## 6. 角色、枪械与动画的制作顺序

先完成一个能出生和移动的角色，再增加一把枪，再补完整表现。不要先把所有动画接完才开始服务器逻辑。

1. 核对骨骼、动画父类、右手持枪 Socket、左手握点、枪口与相机位置。旧路线已记录部分 Lyra 父类缺失，此次未在编辑器重验，作为阶段 0 必查项。
2. 第一人称本地外观与第三人称世界外观分开处理；世界枪不在自己镜头重复出现，本地手臂不让其他玩家看到。
3. 以 CMC 完成走、跑或静步、跳、蹲；先约定速度、胶囊与视点高度，再微调手感。输入映射从开始就使用动作名称，不硬编码键位。
4. 移动 AnimBP 先做待机、方向移动、跳落、蹲姿；上半身持枪通过分层与移动组合。
5. 战斗表现补装备、开火、空仓、换弹、受击、死亡；依据资源再添加瞄准偏移、左手 IK、转身与第一人称后坐力。
6. 客户端立即反馈开火，服务器检查武器、动作、弹药、射速、序号、瞄准起点和时间，再执行射线与伤害；枪口被墙挡住时不能从镜头越墙开火。
7. 换弹真正完成由服务器计时/状态决定；动画 Notify 用于弹匣、声音等表现。看不到角色或服务器不渲染时也必须完成换弹。
8. 重获相关性时从动作序号和服务器时间恢复动画进度；处理武器引用比角色晚到达，不能从头重复换弹或重复扣弹。

CMC 已有网络移动、预测与纠正路径，首版在其基础上扩展，不另写逐帧坐标 RPC。[Epic CMC 网络说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine)

第一把枪只做即时射线。散布、后坐力、伤害区域和移动精度必须有服务器一致规则；穿墙、弹丸回溯、复杂物理后坐力分别作为后续机制。缺少第一人称动画时明确采用临时表现，不把素材存在当最终质量达标。

## 7. 特色一：比分、场景屏幕与材质联动

数据路径：服务器比赛状态 → 客户端当前快照/变化通知 → HUD 比分、Tab 战绩、场景大屏、材质效果。四种表现读取同一事实。

第一版分三步：

1. 复用并检查现有 `WBP_Scoreboard`：队伍、比分、阶段、倒计时正确；战绩只显示允许公开的信息。
2. 场景屏幕使用世界空间 Widget Component 显示数字与队名。其机制适合世界内 UI；先限制重绘频率和绘制尺寸。[Epic Widget Component](https://dev.epicgames.com/documentation/en-us/unreal-engine/widget-components-in-unreal-engine)
3. 屏幕外框/灯带使用动态材质实例，输入领先队颜色、分差、阶段、得分脉冲。数字排版由 UI 处理；若屏幕必须贴合特殊模型 UV，再引入 Render Target 贴图方案。

建议事件效果：比分相同为中性色；领先采用固定队伍色；得分产生短促脉冲；最后阶段提示闪动；比赛结束保持获胜队样式。晚加入只显示当前状态，不能把历史每次得分脉冲重播一遍。

本地翻页、查看战绩是本地 UI 操作；所有玩家共享屏幕页才由服务器同步。若要用射击/按键触发机关，需要服务器校验距离、视线、权限和冷却，材质本身不能决定玩法结果。

注意：屏幕发光可能通过 Lumen 影响周边照明，因此亮度和闪烁需要上限；低画质下比分可读、对战视认公平。每块屏幕用自己的动态实例，避免改共享材质导致全场错误联动。

验收：双端、换边、回合结束、晚加入都显示同一比分；玩家切页不能改分；屏幕不泄露敌方装备/位置；远处屏幕不持续高成本重绘。

## 8. 特色二：可扩展的自定义道具

先选三个具体道具描述，再确定技术路线。这是减少重构最重要的早期决策之一。

| 首批需求 | 推荐路线 | 需要承担的成本 |
|---|---|---|
| 少量投掷/放置/脉冲道具，简单次数与冷却 | 装备数据 + 小型执行组件 + 独立效果 Actor | 维护有限的动作、取消和恢复规则 |
| 多角色技能、被动、叠层、驱散、复杂属性与效果组合 | 在批量实现前评估 GAS 原型 | 学习 ASC、属性、效果、标签及预测；统一状态所有权 |
| 玩家在游戏内编辑和组合技能 | 单独立项定义组合限制、校验和存档 | 超出普通道具配置，不能靠增加几个蓝图字段解决 |

GAS 提供能力、属性与 Gameplay Effects 等机制，适合复杂效果组合；它不自动补齐命中回溯、迷雾与爆破规则。[Epic GAS 概述](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-ability-system-for-unreal-engine)

默认按少量道具方案规划。若早期需求确认属于复杂技能，在阶段 0 定方案、阶段 2 确定生命等状态归属之前完成最小技术试验，避免先做一整套属性系统再迁移。

每个道具定义至少包含：稳定 ID、名称图标、模型、使用方式、价格/次数、使用与冷却时长、合法阶段、效果参数、动画音效、死亡和回合结束处理。运行时保存实例持有者、次数、动作序号、冷却期限及有效效果引用；静态数据资产不保存当前弹药或冷却。

统一执行链：输入意图 → 服务器合法性检查 → 扣除消耗并开始动作 → 生成/激活效果 → 按权限复制 → 到期/取消/清理。扣除时点和取消退还规则逐道具写清，重复请求不能重复扣除或生成。

建议验证顺序（都是候选设计，不表示对应资产存在）：

1. 简单投掷伤害道具：验证轨迹、碰撞、服务器爆炸伤害和统一死亡入口；先用简单服务器投射物，必要时再补本地投掷预测。
2. 侦察脉冲：验证按规则产生有时效、有精度限制的标记；不为了一个地图圆点复制完整敌人 Actor。
3. 烟雾：服务器维护独立的范围、起始时间和生命周期，客户端 Niagara 消费这些数据；明确烟雾对视野、侦察和信息下发的影响。

烟雾不能只靠客户端粒子挡画面，也不能让低画质直接看穿。动态烟雾必须参与迷雾策略失效与重算。部署物的所属队伍、敌方可见条件、可破坏性和回合清理都要逐项定义。

验收：新增同机制道具只添加数据和资源；新机制主要增加局部执行行为。新增一个道具不应修改比赛胜负、所有 HUD、角色移动和全局复制规则。

## 9. 特色三：战争迷雾、小地图和网络体验

### 9.1 先统一“谁有权知道什么”

| 信息 | 首版接收规则建议 | 不应发生的情况 |
|---|---|---|
| 自己、队友 | 允许必要的实时状态；地图显示队友位置 | 队友数据混入敌方连接 |
| 正常可见敌人 | 服务器基于合法视点和保守可见性允许实体状态 | 玩家已看见人，模型仍晚出现 |
| 遮挡敌人 | 不继续发送未授权新坐标/动作；允许有记录的有限预揭示 | 仅隐藏 Mesh，但坐标仍持续下发 |
| 队友发现敌人 | 默认分享有限标记，精度与时效明确 | 全队自动获得敌人持续精确 Actor |
| 侦察 | 按道具规则授权标记或明确的其他信息 | 道具失效后仍继续追踪 |
| 枪声/脚步 | 允许的一次性声源信息 | 声音使完整敌人对象长期相关 |
| 死亡观战 | 仅服务器授权的队友视点 | 客户端任意移动相机探测世界 |
| 世界公共屏幕 | 仅公共比分/战绩 | 显示一支队伍专属的情报 |

迷雾策略与复制接入口分开：策略返回允许的信息、原因和失效条件；复制后端消费结果。阶段 0 读取实际 NetDriver 与日志；传统复制先评估 relevancy，不能在 Iris 下照搬同一个入口。Iris 与 Replication Graph 的迁移约束以官方说明为准，不同时作为一个 NetDriver 的复制方案。[Epic Iris 迁移说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/migrate-to-iris-in-unreal-engine)

第一版在白模角落验证：保守候选筛选、必要遮挡查询、缓存、有限预揭示和隐藏滞后；既不把一条中心射线当可见性证明，也不立即建设全地图离线 PVS。记录提前暴露的时间与原因，不能宣称绝对零泄露。

过滤范围覆盖人物、携带武器、附件、声音、RPC、调试消息和 UI 数据。停止复制不等于旧 Actor 立即消失，必须处理旧位置残留、碰撞和重新初始化。服务器继续模拟隐藏目标；不能因客户端不可见而停止权威命中体更新。

### 9.2 左上角小地图

先采用静态俯视底图 + 世界坐标映射 + 图标层。首版不需要持续 SceneCapture；这也减少把未授权 Actor 渲染进地图的风险。若现有关卡有上下层，增加楼层规则或高度指示。

地图配置保存实际关卡的原点、朝向、缩放、边界和包点数据；不能将某一张地图的坐标写在 Widget 中。界面依次加入：自己/队友 → 包点 → 已授权炸弹信息 → 发现/侦察标记 → 用户 Ping。

敌人标记必须来自服务器授权记录，包含最后观察位置、采样时间与过期时间；失去视野后不能借真实 Actor 继续插值追踪。首版是否自动显示自己看见的敌人、是否向队友共享、开火是否亮点，均是显式玩法规则。

客户端 Ping 也需校验距离、频率与内容；炸弹携带者、掉落位置、安装点是否全员知晓分别定义。HUD 的“实时”指及时显示允许的信息，不代表显示完整服务器世界。

### 9.3 网络体验从第一把枪开始

- 移动用 CMC 预测与平滑；特殊冲刺、位移技能接入其重演路径后再发布。
- 本地开火即时表现，服务器权威判定；用 ShotId/动作序号确认、拒绝与去重，预测命中提示不冒充权威伤害。
- 自动射击必须能恢复丢失的停止输入；死亡、换枪、换回合、失去焦点也停止合法开火状态。
- 长动作按快照恢复，枪声/火花等瞬时事件不过期补播；避免每帧 Reliable RPC 和全场 Multicast。
- 基础射线可靠后加入有界历史回溯；记录时间、命中体和生命标识，限制历史窗口与请求频率，复活/瞬移断开历史。
- 第一版回溯明确支持静态遮挡；动态门、移动掩体、穿墙和投射物须另定义历史碰撞语义。不能通过迷雾禁止合法盲射。

独立服务器是正式验收环境。Listen Server 可开发，但房主进程本身拥有服务器状态，不能承诺对房主同等信息隔离。

## 10. 基础设置、音效与沟通

输入架构在角色阶段接入，设置菜单在完整爆破闭环后补齐，避免到末期才重做输入。

| 分类 | 首版功能 | 验收重点 |
|---|---|---|
| 键位 | 移动、跳蹲/静步、射击、换弹、切枪、道具、交互、战绩、购买、菜单 | 主/备用键、冲突提示、恢复默认、重启后保留 |
| 鼠标 | 灵敏度、反转 Y、按需加入瞄准倍率 | 帧率变化不改变预期输入；UI 不误触发开枪 |
| 画面 | 分辨率、显示模式、帧率上限、垂直同步、质量档 | 分辨率应用确认与超时恢复；不同画质保持玩法遮挡 |
| HUD | 准星、地图缩放/旋转、必要的色觉辅助 | 设置重载、不同分辨率与 DPI 可读 |
| 音量 | 总音量、玩法音效、环境、音乐、UI | 设置保存；关键提示不被混音预算挤掉 |
| 网络提示 | 实测 Ping、FPS、连接异常 | 失败反馈与返回流程，避免只显示“连接中” |
| 沟通 | 首版队伍 Ping/快捷消息 | 接收队伍正确、限频；语音随后单独接服务与设备设置 |

使用 Enhanced Input 的映射与用户设置机制；官方 `UEnhancedInputUserSettings` 提供映射档案、应用和保存相关 API，具体启用及持久化在本机 5.8 验证。[Epic 输入用户设置](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/EnhancedInput/UEnhancedInputUserSettings)

声音按用途组织：本地开火反馈、远处武器声、脚步/落地、换弹/切枪、炸弹、道具、环境/UI。脚步按地面物理材质选择，空间声音使用距离衰减与遮挡；脚步节奏与服务器事件规则一致，不能依赖隐藏 Mesh 的本地 Notify 是否运行。[Epic 声音衰减](https://dev.epicgames.com/documentation/en-us/unreal-engine/sound-attenuation-in-unreal-engine)

如果瀑布声承担“掩盖脚步”的竞技作用，允许单独关闭它就会产生优势。应将相关声音归入一致的玩法混音规则，或将瀑布明确为不承担战术遮蔽的装饰音。语音聊天、匹配、账号、举报及完整反作弊属于后续发布服务，不将迷雾当完整反作弊方案。

## 11. 瀑布、水面与关卡表现

先在阶段 0 标出位置及玩法边界，表现制作可在核心协议稳定后独立推进。

| 场景需求 | 首选小实现 | 升级条件 |
|---|---|---|
| 工厂水池、小面积水面 | 网格 + 水材质 + 波纹/泡沫参数 | 需要连续大型水域与岸线时再评估 Water System |
| 垂直瀑布 | 水幕网格与流动材质 + Niagara 水花/雾气 + 环境声 | 只有玩法确需流体交互才评估实时流体 |
| 浅水脚步/弹着 | 已授权事件驱动局部涟漪和水花 | 不复制粒子本身 |
| 河湖/复杂岸线 | 调研 Water System 的水体与地形工作流 | 验证当前地图与插件成本后引入 |

Epic 提供 Single Layer Water、水系统及 Niagara；本项目采用哪一种由水体规模决定，不将 Water 插件视为瀑布的必要依赖。[Single Layer Water](https://dev.epicgames.com/documentation/en-us/unreal-engine/single-layer-water-shading-model-in-unreal-engine)、[Water System](https://dev.epicgames.com/documentation/en-us/unreal-engine/water-system-in-unreal-engine)、[Niagara](https://dev.epicgames.com/documentation/en-us/unreal-engine/creating-visual-effects-in-niagara-for-unreal-engine)

当前配置启用了 Substrate、Lumen 等选项，先做小面积材质兼容与性能样板，不为一个水效果全局更换渲染设置。

服务器仅管理水域碰撞、伤害/减速等实际玩法状态；纯装饰特效不在 Dedicated Server 运行。水雾若真正阻挡视线，必须有明确且与画质无关的玩法体积和迷雾规则；粒子的随机形状不能决定服务器可见性。

验收：近远景和低高画质一致可玩；透明叠加与反射成本可测；声音不淹没必要提示；瀑布背后、边缘露头、隔水射击和迷雾行为符合预先写明的规则。

## 12. 分阶段执行与完成标准

以下沿用仓库阶段编号，新增功能作为子阶段插入。每个子阶段都以一个可以运行演示的小增量交付。

| 阶段 | 任务与交付 | 进入后续阶段的条件 |
|---|---|---|
| 0A 现场与规则 | 资产依赖、真实 GameMode/出生点/包点；整理规则表；列出首批三个道具；确定水与屏幕玩法 | 有问题清单和可执行的首版规则，没有伪造资产与位置 |
| 0B 网络与构建基线 | 服务器 + 两客户端，大厅切图、身份交接、实际复制后端；尽早试 Server/Client Cook | 连接与切图有记录；构建/资源阻塞先处理 |
| 1A FPS 身体 | 比赛 Pawn、CMC、相机、输入、出生、基础走跳蹲 | 双端移动/控制权正确，大厅到比赛不丢队伍 |
| 1B 基础动画 | 本地/远端外观、移动 AnimBP、持枪 Socket 与最小瞄准 | 自己不看见重复模型，远端姿态和枪口合理 |
| 2A 一把枪 | 数据、装备、射线、生命、死亡、弹药、换弹 | 双端伤害一致，非法/重复开火拒绝 |
| 2B 表现与恢复 | 本地开火反馈、动作序号、换弹打断、最小血量弹药 HUD | 延迟下立即反馈，重建角色可恢复当前动作 |
| 3A 迷雾基础 | 现有地图遮挡测试、人物/附件过滤、预揭示、状态重建 | 接收记录不含未授权新位置，合法目标及时出现 |
| 3B 信息接入 | 队友地图、授权标记通路、声音权限和受限观战基础 | 小地图、声音、观战不绕过实体过滤 |
| 4 弱网与回溯 | 网络矩阵、有界历史、时间/生命/序号校验、拒绝校正 | 状态可恢复，掩体后受击与命中差异有数据 |
| 5A 完整爆破 | 持弹/掉落/拾取/安装/拆除、死亡胜负、重生重置、换边、结束返回 | 两客户端能完成整场，不重复结算，不遗留上回合动作 |
| 5B 比分与 UI | 完成战绩 HUD、世界大屏、材质联动、目标提示和地图图标 | 晚加入/换边一致；公共屏幕不显示私有情报 |
| 5C 经济与装备扩展 | 购买范围/时限、资金、奖励、保枪、第二种装备 | 重复购买不扣两次/多生成；换边和断线不复制物品 |
| 5D 道具 | 按第 8 节逐个加入；每个都验证死亡/回合清理/信息权限 | 第二个同机制道具不修改无关系统，烟雾与侦察规则一致 |
| 5E 设置与场景表现 | 完整设置页、混音、瀑布/水材质、美术动画打磨 | 保存恢复正常，画质不改变竞技遮挡，新增特效预算达标 |
| 5F 六人与地图平衡 | 六人完整流程、出生到点时间、转点/回防、道具与帧耗时 | 六人比赛无流程卡死；迷雾与性能有实测结果 |
| 6 独立交付 | Server/Client 构建、Cook/打包、跨机、长时间回归 | 不依赖编辑器运行，功能与网络检查在打包版通过 |

阶段 0 可画屏幕和水的视觉草案；阶段 2 可验证比分数字的临时显示；正式制作仍在表中对应阶段。基础 UI、输入设置入口和声音反馈提前接入，避免全部推到最后。阶段 6 是最终验收，不是第一次尝试打包。

### 每次教学/实施的固定交付

1. 明确本次可看到的一个结果、前置条件和暂未支持项。
2. 指出真实文件/资产；说明输入到服务器到客户端的完整数据流。
3. 做必要代码与编辑器配置，复用已有类，不重复搭框架。
4. 给正常、异常、弱网三类运行步骤；简单内容可只做适当手动检查。
5. 保存结果、日志路径和待解决问题；验收未过不扩大相依功能。

## 13. 验收清单与性能预算

### 13.1 功能边界

- 比赛：正常安装/拆除、取消/接续、最后时刻安装、拆除/爆炸同刻、装后进攻方全灭、无人参战、重复结算。
- 战斗：空弹、换弹切枪、死亡取消、停止开火包丢失、重复射击请求、墙边枪口、上一条生命的过期请求。
- 生命周期：新回合清理掉落物/投射物/持续效果/Timer，按规则保枪与保留经济；不清掉整场统计。
- 信息：转角、跳跃露头、快速转头、迷雾中换弹、武器晚到达、声音、侦察过期、烟雾开关、队伍变更与观战切换。
- UI：HUD/大屏/材质一致，失去视野后小地图不过度更新，晚加入不重播旧事件。
- 连接：加载超时、断线/重连、旧连接失效、新加入观战、回大厅再开一局；身份验证不能用客户端随意填写的昵称代替。
- 设置/表现：改键冲突、菜单焦点、重启保存、低高画质、水幕后目标可见性、音频设置公平性。

只验收已经实现的功能；动态门、穿墙、游泳等未支持项明确标记，不填写“通过”。

### 13.2 网络条件

| 条件 | 目标实测 RTT | 抖动/丢包 | 必须观察 |
|---|---|---|---|
| 基线 | 本地低延迟 | 无人工丢包 | 权限、阶段、装备一致 |
| 常规 | 约 50 ms | 小抖动、0–1% 丢包 | 开火响应与远端平滑 |
| 弱网 | 约 100 ms | 约 20 ms 波动、1–3% 丢包 | 纠正、换弹/拆弹取消、标记过期 |
| 压力 | 约 150–200 ms | 较大波动、5% 丢包、短时中断 | 恢复与拒绝策略，无永久卡死 |

以上是项目测试条件，不是已实现的体验保证。按实测 Ping 区分 RTT 与单向延迟，补充不对称和突发丢包。Epic 的 Network Emulation 支持模拟收发延迟与丢包，可用于此矩阵。[Epic 网络模拟](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-network-emulation-in-unreal-engine)

首期服务器目标六人、60 Hz，处理帧预算约 16.67 ms；统计排除主动等待后的 P50/P95/P99 与超预算次数。迷雾暂争取 P95 不超过此预算 5%，约 0.83 ms，未达标先剖析，不立刻更换复制框架。

客户端目标硬件尚未确定，先记录现有白模的 CPU/GPU 帧耗时基线，再给大屏、水、烟雾分配预算。转角出现延迟、纠正次数/距离、每连接上下行、RPC 流量、可靠队列都需测量；不能仅凭平均 FPS 判定“网络好”。

每份报告记录：提交/构建版本、UE 版本、地图、人数、硬件、画质、网络参数、实测 RTT、时长和日志。至少独立服务器 + 两独立客户端，之后六人和真实跨机。迷雾同时检查客户端接收数据与可见性录像。

## 14. 工作量与控制范围

以下是单人开发、能够稳定投入、尽量复用现有素材时的粗略有效工作日估算，不是排期承诺。学习 UE、资产返修、缺资源或外部联机服务可能明显增加时间。

| 工作包 | 粗略工作日 |
|---|---|
| 阶段 0：现状、规则、启动与资产 | 3–6 |
| 阶段 1：角色和基础动画 | 5–10 |
| 阶段 2：一把枪闭环 | 8–15 |
| 阶段 3：迷雾与最小信息链 | 10–20 |
| 阶段 4：弱网和回溯 | 10–20 |
| 阶段 5A：完整爆破循环 | 8–15 |
| 阶段 5B/C：UI、大屏、经济装备 | 8–15 |
| 阶段 5D：少量道具 | 8–15 |
| 阶段 5E：设置、音效、水与表现 | 8–15 |
| 阶段 5F/6：六人、打包、跨机回归 | 10–20 |

合计约 78–151 个有效工作日，尚不含额外缓冲；按实际经验可预留 25%–40% 给资产和网络问题。核心原型会早于全部功能完成。先完成阶段 0–2，再用真实速度调整后续估算；不同时制作所有枪、所有技能和整张地图的最终美术。

阶段 3/4 是技术风险较高的工作包，提前完成小场景验证。主要变更触发点只有：道具复杂度需要 GAS、实测复制成本需要后端调整、地图规模需要 PVS、玩法需要动态遮挡历史。每次写明现有问题、最小改动和兼容方案，而不是预先建设所有替代框架。
